Di sini kita akan explore lebih dalam lagi configuration dan property-property yang ada pada
docker-compose.yaml, dan apa yang bisa kita lakukan untuk mempermudah multi container implementation.

Kita akan mempelajari attribute-attribute yang sering dipakai dalam project dengan contoh-contoh sederhana
yang bisa ditemukan di Guides/ComposeLinux dan kebanyakan di Guides/ComposeProjects 


-------------------------------------------------------------------------------------------------------------------------
1. services

Pada percobaan di chapter sebelumnya, kita sudah melihat attribute services yang muncul paling di file yaml.
Services adalah collection of service, tetapi pada yaml services lebih ditulis dalam bentuk object ketimbang array.
Itu dikarenakan docker compose ingin membuatkan key-value pair collection pada service, tetapi tidak ada
collection sejenis map pada yaml. Akhirnya dibuatkanlah dalam bentuk attribute-value untuk menggantikan key-value.
Jadi setiap nama service adalah ID atau Key yang dituliskan dalam attribute. Karena sifatnya seperti Key atau ID,
nama service bersifat unik dan tidak boleh sama satu sama yang lain.

Oleh karena digunakan sebagai ID dan sifatnya harus unik, nama service disebut juga sebagai Service Identifier.
Kesalahan yang sering terjadi adalah banyak yang men-salah artikan kalau service itu sama dengan container.

Service adalah definisi atau blueprint dalam Docker Compose yang menjelaskan bagaimana satu jenis container 
harus dibangun atau dijalankan, termasuk image yang digunakan, konfigurasi, jaringan, volume, port, environment variable, 
dan pengaturan lainnya. Jadi service bukanlah container, tetapi konfigurasi komplit sampai rumah itu selesai.
Bayangkan kalau kalian membeli lemari dari IKEA, lalu di sana ada buku petunjuk cara merakitnya, bahan-bahannya apa saja yang
sudah disediakan di dalam box? Dan apakah ada tools lain yang diperlukan di luar yang disediakan box? Apakah butuh
tambahan palu? tambahan obeng? Adakah link dalam bentuk QR code yang menampilkan tutorial tambahan dari youtube?

2. container_name

Apabila kita tidak menggunakan attribute container_name, maka nama container kita akan diberikan berdasarkan
nama servicenya (di-concate dengan nama projectnya). Tetapi jika kita berikan nama containernya, nama containernya
tidak akan menggunakan default nama servicenya. Perhatikan contoh Guides/ComposeProjects/hello_system

services:
  helloWorld:
    container_name: hello-world-container
    image: hello-world:latest

  myFedora:
    container_name: fedora-container
    image: fedora:44
    command: sleep infinity

  myUbuntu:
    container_name: ubuntu-container
    image: 'ubuntu:26.04'
    command: sleep infinity

Pada kasus ini, contoh nama services adalah: helloWorld, myFedora, myUbuntu.
Sedangkan nama containernya bisa dilihat: hello-world-container, fedora-container, dan ubuntu-container.

Sebagai contoh yang bertujuan untuk menunjukan perbedaannya, saya menggunakan nama container yang berbeda.
Walaupun tidak ada aturan baku harus seperti apa penulisan, tetapi penulisan nama pada docker, baik image, container, service, project,
biasanya bergantian antara kebab-case dan snake_case.

untuk penamaan image saya biasa menggunakan kebab-case,
untuk penamaan project dan service/container saya menggunakan snake_case.
Jadi ketika pembuatan project saya bisa mudah melihatnya jadi seperti ini:

travel_management-core_backend

Dimana travel_management adalah nama projectnya dan core_backend adalah nama containernya.

services:
  core_backend:

3. image

Attribute image di sini bisa memiliki 2 kegunaan. Dimana kegunaan ini berfungsi bergantian tergantung kehadiran attribute build
(apa itu build nanti dijelaskan di bagian attribute build) di dalam docker compose. Tetapi value dari attribute ini
sudah pasti nama image.

Bila attribute build tidak ada, maka kegunaan image adalah untuk menunjukan image mana yang dipakai untuk proses pembuatan
container ini. 

Bila attribute build ada, maka kegunaan image adalah untuk memberikan nama image baru dari hasil build docker compose ini.
Lalu menggunakan image baru ini untuk pembuatan container baru ini.

4. build

Selain membuat container, kita juga sudah banyak belajar membuat image lewat proses build dengan menggunakan command
docker build yang menggunakan konfigurasi dari Dockerfile. Jadi selain membantu proses pembuatan container dari image,
docker compose juga membantu melakukan proses build untuk sebuah image.

Jadi kesimpulannya, service tidak hanya mengurusi penciptaan container saja, tapi juga dalam proses building image.
Di sini juga kita bisa mengkombinasikan docker compose dengan Dockerfile.

Kita bisa mencoba lihat contoh attribute build dari contoh di dalam directory:
-) Guides/ComposeProjects/static_web
-) Guides/ComposeProjects/static_web_env

services:
  website:
    build:
      context: .
    ports:
      - "8007:80"

services:
  website:
    image: static-we:1.0
    build:
      context: .
      dockerfile: Dockerfile.development
      labels:
        maintainer: "Boby"
        version: "1.0"
        description: "Backend API service"
    ports:
      - "8008:80"
    environment:
      NAME: "Boby Widjaja"
      JOB: "Developer"
      DEPARTMENT: "IT"

Pada 2 contoh di atas, kita bisa melihat docker composenya memiliki attribute build,
dimana attribute build memiliki beberapa attribute lagi. Pada contoh di atas ditampilkan context dan dockerfile.
Berikut ini beberapa attribute dari build yang cukup umum digunakan (tidak semua):

-) context: digunakan untuk menunjukan directory tempat build context disimpan.
-) dockerfile: digunakan untuk menunjukan path dan nama dari Dockerfile yang digunakan.
  Note: bila Dockerfile berada di root context directory dan menggunakan nama default Dockerfile, maka attribute ini tidak diperlukan.
-) args: Digunakan untuk men-supply value-value untuk ARG pada Dockerfile.
-) target: sesekali digunakan untuk multi-stage dockerfile, dimana kita bisa memilih untuk menghasilkan image hanya dari step 1
dari multi-stage tersebut.

FROM node:24 AS base
WORKDIR /app
COPY package*.json ./

FROM base AS development
RUN npm install
COPY . .
CMD ["npm", "run", "dev"]

FROM base AS production
RUN npm ci --omit=dev
COPY . .
CMD ["npm", "start"]

============================

services:
  app:
    build:
      context: .
      target: development

Hasil image hanya sampai build stage 2.

Tetapi tidak cukup di sana, agar command docker bisa melakukan build, kita harus menambahkan option build
pada command docker compose up.
docker compose up --build

atau secara alternatif, kita bisa proses build dulu, baru di up kemudian.
docker compose build
docker compose build --no-cache (Bila tidak mau ada cache pada build berikutnya)

5. ports

Sama seperti pada dockerfile, kita juga bisa publish ports lewat docker compose configuration.
Kita bisa melakukannya dengan menggunakan ports attribute. Kurang lebih seperti ini contohnya:

services:
  website:
    build:
      context: .
    ports:
      - "8007:80"

Contoh ini bisa dilihat di Guides/static_web.

Service juga bisa menggunakan multiple ports, seperti contohnya:
services:
  myapp:
    image: myapp:1.0
    ports:
      - "8007:80"
      - "8443:443"
      - "9000:9000"

Mengapa satu container bisa punya banyak port?
Karena satu aplikasi/service bisa menyediakan beberapa endpoint jaringan.

Contoh klasik Nginx:
80   → HTTP
443  → HTTPS

6. command

Command di dalam docker compose simplenya adalah command yang dijalankan ketika container di jalankan.
command yang biasa diketik pada saat docker run atau docker start.
docker run ....... [command]
docker start ...... [command]
Dari pelajaran Dockerfile, kita tau command ini adalah command yang akan meng-override CMD instruction (bukan ENTRYPOINT)

services:
  app:
    image: myapp
    command: "echo A && echo B"

Ada beberapa syntax penulisan dari command pada docker compose:

Type 1: Flow Sequence (Array Style)
command: ["python", "app.py"]

Type 2: String
command: python app.py

Type 3: Block Sequence (List Style)
command:
  - python
  - app.py
  - --port
  - "8080"
