Di sini kita akan explore lebih dalam lagi configuration dan property-property yang ada pada
docker-compose.yaml, dan apa yang bisa kita lakukan untuk mempermudah multi container implementation.

Kita akan mempelajari attribute-attribute yang sering dipakai dalam project dengan contoh-contoh sederhana
yang bisa ditemukan di Guides/ComposeLinux dan kebanyakan di Guides/ComposeProjects 


-------------------------------------------------------------------------------------------------------------------------
1. services

Pada percobaan di chapter sebelumnya, kita sudah melihat attribute services yang muncul di paling awal file yaml.
Services adalah collection of service, tetapi pada yaml services lebih ditulis dalam bentuk object ketimbang array collection.
Itu dikarenakan docker compose ingin membuatkan key-value pair collection pada service, tetapi tidak ada
collection sejenis map pada yaml. Akhirnya dibuatkanlah dalam bentuk attribute-value untuk menggantikan key-value.
Jadi setiap nama service adalah ID atau Key yang dituliskan dalam attribute. Karena sifatnya seperti Key atau ID,
nama service bersifat unik dan tidak boleh sama satu sama yang lain.

Oleh karena digunakan sebagai ID dan sifatnya harus unik, nama service disebut juga sebagai Service Identifier.
Kesalahan yang sering terjadi adalah banyak yang men-salah artikan kalau service itu sama dengan container.

Service adalah definisi atau blueprint dalam Docker Compose yang menjelaskan bagaimana satu jenis container 
harus dibangun atau dijalankan, termasuk image yang digunakan, konfigurasi, jaringan, volume, port, environment variable, 
dan pengaturan lainnya. 

Jadi sebuah service bukanlah sebuah container, tetapi konfigurasi komplit dari proses build sampai menjalankan container.
Bayangkan kalau kalian membeli lemari dari IKEA, lalu di sana ada buku petunjuk cara merakitnya, bahan-bahannya apa saja yang
sudah disediakan di dalam box? Dan apakah ada tools lain yang diperlukan di luar yang disediakan box? Apakah butuh
tambahan palu? tambahan obeng? Adakah link dalam bentuk QR code yang menampilkan tutorial tambahan dari youtube?
List kebutuhan dan buku petunjuk inilah service.

2. container_name

Apabila kita tidak menggunakan attribute container_name, maka nama container kita akan diberikan berdasarkan
nama servicenya (di-concate dengan nama projectnya). Contoh:
nama project: my_laundry
nama service: backend 
nama default container: my_laundry-backend

Tetapi jika kita berikan nama containernya, nama containernya
tidak akan menggunakan default nama servicenya. Perhatikan contoh Guides/ComposeProjects/hello_system

services:
  helloWorld:
    container_name: hello-world-container
    image: hello-world:latest

  myFedora:
    container_name: fedora-container
    image: fedora:44
    command: sleep infinity

  myUbuntu:
    container_name: ubuntu-container
    image: 'ubuntu:26.04'
    command: sleep infinity

Pada kasus ini, contoh nama services adalah: helloWorld, myFedora, myUbuntu.
Sedangkan nama containernya bisa dilihat: hello-world-container, fedora-container, dan ubuntu-container.

Sebagai contoh yang bertujuan untuk menunjukan perbedaannya, saya menggunakan nama container yang berbeda.
Walaupun tidak ada aturan baku harus seperti apa penulisan, tetapi penulisan nama pada docker, baik image, container, service, project,
biasanya bergantian antara kebab-case dan snake_case.

untuk penamaan image saya biasa menggunakan kebab-case,
untuk penamaan project dan service/container saya menggunakan snake_case.
Jadi ketika pembuatan project saya bisa mudah melihatnya jadi seperti ini:

travel_management-core_backend

Dimana travel_management adalah nama projectnya dan core_backend adalah nama containernya.

services:
  core_backend:

3. image

Attribute image di sini bisa memiliki 2 kegunaan. Dimana kegunaan ini berfungsi bergantian tergantung kehadiran attribute build
(apa itu build nanti dijelaskan di bagian attribute build) di dalam docker compose. Tetapi value dari attribute ini
sudah pasti nama image.

Bila attribute build tidak ada, maka kegunaan image adalah untuk menunjukan image mana yang dipakai untuk proses pembuatan
container ini. 

Bila attribute build ada, maka kegunaan image adalah untuk memberikan nama image baru dari hasil build docker compose ini.
Lalu menggunakan image baru ini untuk pembuatan container baru ini.

4. build

Selain membuat container, kita juga sudah banyak belajar membuat image lewat proses build dengan menggunakan command
docker build yang menggunakan konfigurasi dari Dockerfile. Jadi selain membantu proses pembuatan container dari image,
docker compose juga membantu melakukan proses build untuk sebuah image.

Jadi kesimpulannya, service tidak hanya mengurusi penciptaan container saja, tapi juga dalam proses building image.
Di sini juga kita bisa mengkombinasikan docker compose dengan Dockerfile.

Kita bisa mencoba lihat contoh attribute build dari contoh di dalam directory:
-) Guides/ComposeProjects/static_web
-) Guides/ComposeProjects/static_web_env

services:
  website:
    build:
      context: .
    ports:
      - "8007:80"

services:
  website:
    image: static-we:1.0
    build:
      context: .
      dockerfile: Dockerfile.development
      labels:
        maintainer: "Boby"
        version: "1.0"
        description: "Backend API service"
    ports:
      - "8008:80"
    environment:
      NAME: "Boby Widjaja"
      JOB: "Developer"
      DEPARTMENT: "IT"

Pada 2 contoh di atas, kita bisa melihat docker composenya memiliki attribute build,
dimana attribute build memiliki beberapa attribute lagi. Pada contoh di atas ditampilkan context dan dockerfile.
Berikut ini beberapa attribute dari build yang cukup umum digunakan 
(saya tidak menampilkan semua attribute yang available di dokumentasi):

-) context: digunakan untuk menunjukan directory tempat build context disimpan.
-) dockerfile: digunakan untuk menunjukan path dan nama dari Dockerfile yang digunakan.
  Note: bila Dockerfile berada di root context directory dan menggunakan nama default Dockerfile, maka attribute ini tidak diperlukan.
-) args: Digunakan untuk men-supply value-value untuk ARG pada Dockerfile.
-) target: sesekali digunakan untuk multi-stage dockerfile, dimana kita bisa memilih untuk menghasilkan image hanya dari step 1
dari multi-stage tersebut.

FROM node:24 AS base
WORKDIR /app
COPY package*.json ./

FROM base AS development
RUN npm install
COPY . .
CMD ["npm", "run", "dev"]

FROM base AS production
RUN npm ci --omit=dev
COPY . .
CMD ["npm", "start"]

============================

services:
  app:
    build:
      context: .
      target: development

Hasil image hanya sampai build stage 2.

Tetapi tidak cukup di sana, agar command docker bisa melakukan build, kita harus menambahkan option build
pada command docker compose up.
docker compose up --build

atau secara alternatif, kita bisa proses build dulu, baru di up kemudian.
docker compose build
docker compose build --no-cache (Bila tidak mau ada cache pada build berikutnya)


-------------------------------------------------------------------------------------------------------------------------
5. command

Command di dalam docker compose simplenya adalah command yang dijalankan ketika container di jalankan.
command yang biasa diketik pada saat docker run atau docker start.
docker run ....... [command]
docker start ...... [command]
Dari pelajaran Dockerfile, kita tau command ini adalah command yang akan meng-override CMD instruction (bukan ENTRYPOINT)

services:
  app:
    image: myapp
    command: "echo A && echo B"

Ada beberapa syntax penulisan dari command pada docker compose:

Type 1: Flow Sequence (Array Style)
command: ["python", "app.py"]

Type 2: String
command: python app.py

Type 3: Block Sequence (List Style)
command:
  - python
  - app.py
  - --port
  - "8080"

6. volumes

Kita juga bisa menggunakan attribute volumes untuk melakukan konfigurasi volume.
Volumes di declare dan di set di lokasi yang berbeda. Di declare selevel dengan services dan di set
di bawah satu service yang dituju, contoh seperti di bawah ini:

services:
  database:
    image: mysql:9.7
    container_name: mysql_container
    ports:
      - "3306:3306"
    environment:
      MYSQL_ROOT_PASSWORD: nodecomplete
    volumes:
      - mysql_volume:/var/lib/mysql

volumes:
  mysql_volume:

Kalian bisa lihat contohnya di Guides/ComposeProjects/basilisk.
Ini adalah versi complete project yang pernah dibuat sebelumnya di Guides/BasiliskSpring.

services:
  basilisk_db:
    volumes:
      - sqlserver_vol:/var/opt/mssql

volumes:
  sqlserver_vol:

Selain dengan penulisan:
  - sqlserver_vol:/var/opt/mssql

Kita juga bisa menulis long format seperti:
  - type: volume
    source: sqlserver_vol
    target: /var/opt/mssql

Untuk melihat contoh yang bind mount bisa dilihat di Guides/ComposeProjects/basilisk_bind

basilisk_db:
  volumes:
    - type: bind 
      source: C:/Binder 
      target: /var/opt/mssql/data


-------------------------------------------------------------------------------------------------------------------------
7. ports

Sama seperti pada dockerfile, kita juga bisa publish ports lewat docker compose configuration.
Kita bisa melakukannya dengan menggunakan ports attribute. Kurang lebih seperti ini contohnya:

services:
  website:
    build:
      context: .
    ports:
      - "8007:80"

Contoh ini bisa dilihat di Guides/static_web.

Service juga bisa menggunakan multiple ports, seperti contohnya:
services:
  myapp:
    image: myapp:1.0
    ports:
      - "8007:80"
      - "8443:443"
      - "9000:9000"

Mengapa satu container bisa punya banyak port?
Karena satu aplikasi/service bisa menyediakan beberapa endpoint jaringan.

Contoh klasik Nginx:
80   → HTTP
443  → HTTPS

8. networks

Network adalah attribute yang digunakan untuk men-set network untuk tiap servicenya.
Walaupun sebenarnya suatu fasilitas dan kemudahan pada docker compose karena network sudah otomatis dibuatkan tanpa
kita harus menulis network attribute. Tapi tentu saja networks attribute perlu untuk deeper configuration
dari network.

Attribute networks ada 2 macam, yaitu networks yang merupakan attribute dari service,
dan networks yang membuat network configuration.

networks (configuration)
attribute ini ditulis sejajar dengan service, bukan attribute dari service.
attribute ini digunakan untuk membuat konfigurasi network, dimana networks sendiri memiliki attribute-attribute
lagi seperti name, driver, external, internal, label, dan lain sebagainya. (Saya tidak list semua, terutama
yang networknya menjadi bagian dari konfigurasi network infrastructure.)

name: adalah nama network yang bisa di set kalau tidak mau menggunakan default nama network yang diberikan compose.
  Jadi sifatnya sama persis dengan container, bila tidak diberikan nama, maka nama akan diberikan secara otomatis
  berdasarkan nama projectnya lalu diberikan nama default.

driver: mengatur jenis driver dari networknya. Jenis-jenis network driver sudah pernah dijelaskan di
  notes dengan nama Networking.txt, kurang lebih bisa di set sebagai bridge, host, none, overlay atau macvlan.

external: External adalah attribute yang digunakan saat container pada docker compose kita ingin menggunakan network yang
  sudah ada sebelumnya, bisa karena dibuat oleh docker network create atau dibuat oleh compose lain. Network ini dikelola di luar lifecycle Compose. 
  Compose hanya menggunakannya dan tidak akan membuat atau menghapusnya.

Misalnya kita sudah membuat:
docker network create basilisk_shared

services:
  basilisk_be:
    image: basilisk-backend:1.0
    networks:
      - basilisk_net
networks:
  basilisk_net:
    external: true
    name: basilisk_shared

atau kalau tidak pakai nama:

services:
  basilisk_be:
    image: basilisk-backend:1.0
    networks:
      - basilisk_shared
networks:
  basilisk_shared:
    external: true


internal: adalah attribute yang mengisolasi sebuah network sehingga tidak bisa terkoneksi dengan koneksi di luar network.
Entah melalui LAN atau internet ke server lain. 
Container yang sudah menggunakan internal network tidak bisa connect dengan API dari luar server, download package apa pun dari internet,
atau mengirim suatu data lewat applikasi apa pun.
Tujuannya menjaga security dengan mengisolasi data di dalam container tidak ada yang bisa keluar dari network surface.


labels: digunakan untuk pemberian metadata pada network bila memang dibutuhkan. Sama seperti label pada container, kita
juga bisa memberi label pada network. contoh:

networks:
  basilisk_net:
    driver: bridge
    internal: true
    labels:
      project: basilisk
      environment: development
      purpose: backend


networks (attribute service): Ini digunakan untuk memasukan container kita ke dalam network yang namanya sudah didefine
  di dalam networks attribute configuration. Nama network bisa ditulis dalam penulisan collection syntax pada service.
  Contoh bisa dilihat di Guides/ComposeProject/basilisk

services:
  basilisk_db:
    networks:
      - basilisk_net

  basilisk_be:
    networks:
      - basilisk_net

  basilisk_fe:
    networks:
      - basilisk_net

networks:
  basilisk_net:
    name: basilisk_net
    driver: bridge

Notes: apa yang terjadi bila salah satu tidak set ke dalam network yang sudah dibut di konfigurasi?
Misalnya saja dari memahami project basilisk, kita tau kalau hubungan antara backend dan frontend tidak melalui
internal container dengan DNS nya docker, tetapi melalui perantara port yang sudah dipublish di host.
Jadi mungkin pertimbagannya, frontend tidak perlu diberikan network, seperti di bawah ini:

services:
  basilisk_db:
    networks:
      - basilisk_net

  basilisk_be:
    networks:
      - basilisk_net

  basilisk_fe:

networks:
  basilisk_net:
    name: basilisk_net

Tapi sebenarnya untuk container yang tidak di set ke dalam defined network di konfigurasi, akan tetap secara otomatis
diberikan dan dibuatkan default network oleh docker compose, sehingga sbnernya hasilnya akan seperti ini:

services:
  basilisk_db:
    networks:
      - basilisk_net

  basilisk_be:
    networks:
      - basilisk_net

  basilisk_fe:
    networks:
      - basilisk_default

9. network_mode

network_mode adalah attribute pada service yang digunakan untuk menentukan model networking yang digunakan oleh container tersebut.
Gunakan network_mode pada saat kita tidak menggunakan networks.
network_mode memiliki beberapa pilihan value, yaitu: bridge, host, none, service:<service>, dan container:<container>.

-) bridge: dengan mode ini, container ini meminta dirinya join network bernama bridge yang selalu ada by default setiap kalian
kita membuat container biasa tanpa menggunakan compose sekalipun. Jadi dia tidak diberikan network default yang digenerate oleh docker compose.

-) host: ini sama dengan penjelasan host pada notes Networking.txt. Artinya container tidak menggunakan ip address sendiri,
melainkan menggunakan address milik hostnya. Sehingga pengaturan expose dan publishing port tidak berguna bagi network ini.

-) none: artinya container tidak dapat network docker sama sekali. Dengan begini bukan hanya komunikasi antar container pun yang tidak memungkinkan,
container juga tidak dipublish ke host, tidak bisa terknoneksi dengan internent ataupun jaring lain. Service ini akan membuat
container total terisolasi, dan hanya bisa berkomunikasi dengan dirinya sendiri. Sama seperti none pada penjelasan Networking.txt.

-) other container / service:<service> : dimana sebuah container nebeng network namespace dari container lain, sehingga ip address,
pengaturan port koneksi ke network, semuanya ikut dengan network utamanya.

services:
  backend:
    image: my-backend:1.0
    ports:
        - "8007:8000"
        - "8008:8001"
  frontend:
    image: my-frontend:1.0
    network_mode: "service:backend"

Dalam hal ini frontend akan total ikut network namespace milik backend.
Sama halnya dengan tipe pengaturan host dimana container total nebeng network source milik host, kalau yang ini
ikut pengaturan container tetangganya. Ini hanya digunakan untuk keperluan tertentu dan design network pattern tertentu.

-) other container / container:<container>
Ini sama persis dengan service:<service>, bedanya saja syntax "container:backend" menunjuk ke existing container yang
sudah ada, bukan ke service yang dijalankan bersama.

10. depends_on

depends_on adalah attribute dari sebuah service yang mengatur urutan mulai dijalankannya sebuah service terhadap service lain.
Karena banyaknya service yang jalan hidupnya kebergantungan dengan existensi container yang dihasilkan service lain.
Contoh saja sebuah service applikasi harus menunggu service database menciptakan container databasenya, baru aplikasi itu bisa
berjalan dengan lancar.

Contoh command:
services:
  app:
    depends_on:
      - mysql
  mysql: 
    image: mysql

Kalian bisa melihat contoh langsungnya di Guides/ComposeProjects/basilisk, di sana 
service frontend akan berjalan 

services:
  app:
    depends_on:
      mysql:
        condition: service_healthy
