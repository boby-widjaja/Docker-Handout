============= Introduction =============

Pada chapter ini kita akan mempelajari tentang Container Orchestration dengan menggunakan Docker Swarm.

Container Orchestration adalah cara dan proses mengelola banyak container secara cepat dan otomatis,
terutama kalau container tersebut jalan di banyak host.

Orchestration tools bisa diibaratkan seperti dirigen atau maestro di dalam suatu team besar orchestra,
dimana dia akan membantu kita untuk memanage banyak container ini dengan peranannya masing-masing.
Orchestration tools datang dari bermacam-macam brand dan nama, seperti:
Kubernetes, Nomad, Amazon ECS, Azure AKS, Google GKE, OpenShift, dan lain-lain.
Tapi untuk pelajaran kita kali ini, karena kita mau keept it simple untuk pengenalan, kita menggunakan Orchestration
bawaan dari Docker, yaitu Docker Swarm, atau lebih tepatnya Docker Swarm Mode.
Docker Swarm Mode adalah fitur orchestration yang dibangun langsung ke Docker Engine.

Untuk kasus sederhana dimana kita hanya menggunakan 3 container untuk satu database, satu backend, dan satu
frontend, kebutuhan Orchestration menjadi kurang nyata, tetapi bagaimana kalau aplikasi kita membutuhkan:
5 container frontend
10 container backend
3 container worker
2 database
dan semuanya tersebar di 5 server berbeda?
Terutama mungkin kalau backendnya micro-services architecture.

Dari kebutuhan itu Docker Swarm Mode memberikan beberapa feature-feature yang bisa membantu kita,
feature-featurenya kurang lebih:

1. Scheduling: scheduling bukan feature untuk penjadwalan, in fact sebenarnya istilah scheduling ini sama sekali
tidak ada hubungannya dengan waktu. Scheduling di sini artinya task dan container ini akan dijalankan dimana.

2. Replica: ini adalah satu feature paling menarik, jadi kita bisa menduplikat container menjadi beberapa kembaran
yang bisa berguna sebagai ban cadangan, sehingga sebuah container bisa High Availability, karena bila ada 1 container yang bermasalah, 
container lain bisa menggantikannya, sehingga down time bisa dicegah.

3. Self-healing: In clase bila salah satu replica container ada yang down, docker swarm mampu membuatkan lagi container yang
down, agar jumlah replica kembali ke jumlah awal sesuai yang diharapkan.

4. Load balancing: banyak replica container yang tersebar di beberapa host bisa saling back up performance satu sama lain,
terutama bila beberapa replica sedang terberatkan karena hal-hal tertentu.

5. Scaling: meningkatkan performance sebuah container dengan menambah jumlah replica di penambahan host baru bisa dilakukan
dengan mudah secara Horizontal Scaling. 
Note: Vertical Scaling mengharuskan sebuah operation stop, melakukan peningkatan terhadap mesin host, lalu me-restart
jalannya system lagi. Horizontal scaling bisa langsung lanjut tanpa adanya proses restart.

6. Networking: Biasanya networking terjadi di dalam satu host yang sama, ini memungkinkan networking terjadi di multiple host.

7. Service Discovery: container yang terhubung ke dalam network yang sama, akan dengan mudah dan otomatis menemukan container
lain hanya dengan nama containernya, tanpa perlu pusing untuk terhubung ke host yang mana atau lagi berkomunikasi dengan replica yang mana.


============= Initiation =============

Awalnya kita bisa check apakah docker swarm active atau tidak dengan menggunakan command:
docker info

Kalau docker swarm belum aktif akan ada status inactive, kalau sudah active akan sebaliknya.
(Swarm: inactive)

Pertama-tama kita harus terlebih dulu mengaktifkan docker swarm dengan command initialization:
docker swarm init

Apa yang terjadi ketika kita mengaktifkan docker swarm?

1) Docker engine berubah, yang tadinya standalone (berdiri sendiri sebagai host docker yang independen),
    menjadi docker yang siap bergabung ke dalam swarm cluster.
2) Docker engine yang menginisiasi swarm pertama kali akan menjadi sebuah Node dan 
    mendapatkan status sebagai Swarm Manager atau menjadi Manager Node.
3) Proses ini akan menghasilkan sebuah join token. Token tersebut bisa dilihat di terminal dengan syntax
    kurang lebih seperti ini:
    docker swarm join --token <TOKEN> <MANAGER-IP>:2377
    docker swarm join --token SWMTKN-1-0kpmyi*** 192.168.65.3:2377
4) Docker menyiapkan mTLS (mutual Transport Layer Security) untuk komunikasi antar node melalui jaringan.
5) Node manager ini mulai menggunakan distributed state store atau tempat menyimpan informasi/state dari cluster.


============= Basic Terminology  =============

Mungkin akan sangat membingungkan untuk belajar Docker Swarm sebelum memahami istilah-istilah
dalam Docker Swarm dan bagaimana cara kerjanya. Berikut ini akan kita jabarkan.

Standalone/ Stand-alone: Kondisi awal docker kita dimana di dalam satu computer (host) kita, memiliki 1 Docker Engine
dimana satu docker engine ini bersifat mandiri mengatur segala sesuatunya seperti container, image, network dan volumes.
Konsep ini kebalikan dari Swarm Cluster.

Swarm Cluster : dalam bahasa indonesia sendiri arti Swarm adalah kawanan atau gerombolan dan
Cluster artinya Kelompok dengan kepentingan yang sama. Jadi Swarm Cluster adalah kawanan banyak Docker Engine
yang membentuk satu kesatuan kelompok untuk menjalankan satu system workload container.
Kawanan docker engine itu bisa berada di dalam computer host atau virtual machine host yang berbeda-beda.

Node: Tetapi ketika bergabung ke dalam kawanan cluster, docker engine tidak bisa bergabung dengan identitas
docker engine. Setiap 1 docker engine akan memiliki 1 identitas Node. Jadi saat di dalam Swarm Cluster setiap 
membernya disebut juga sebagai Node (tentu saja 1 Node berada di dalam 1 Docker Engine dan 1 Docker Engine best practicenya
akan di implementasi pada 1 Host). Jadi bisa dibilang Node adalah tanda anggota sebuah docker engine di dalam satu cluster.

Docker Swarm Cluster
│
├── HOST 1
│   └── Docker Engine #1
│       └── Node 1
│
├── HOST 2
│   └── Docker Engine #2
│       └── Node 2
│
└── HOST 3
    └── Docker Engine #3
        └── Node 3

Sebuah Node memiliki role level keanggotaannya, role-nya bisa Manager atau Worker,
jadi bisa diibaratkan ada Node yang lebih seperti Boss atau Captainnya (Manager), dan 
yang lainnya akan menjadi Anggota atau Pengikutnya (Worker).

Manager Node / Swarm Manager: Node yang bertanggung jawab mengelola dan mengontrol Swarm Cluster
bersama. Karena Manager memiliki kuasa ini, itu artinya manager memiliki fungsi Control Plane.

Control Plane: fungsi yang digunakan untuk mengatur atau mengambil keputusan untuk manage cluster bersama.
Yang diatur kurang lebih seperti feature-feature yang sudah pernah disebutkan sebelumnya seperti Scheduling, 
jumlah Replica, Self-Healing, Load Balancing, Scaling, dan lain sebagainya. Itu artinya worker node tidak
bisa secara langsung mengatur ini semua.

Worker Node: adalah node yang bertugas menjalankan workload atau task-task yang telah diperintahkan
Manager Node lewat kekuasaan Control Plane. Jadi worker node tidak memiliki kekuasaan sebagai pengambil 
keputusan melainkan hanya menerima instruksi, seperti tolong buatkan dan jalankan container seperti ini dan seperti itu.

Note: Tapi jangan salah artikan penjelasan diatas dengan mengatakan peran manager node hanya control plane,
karena manager node juga menjalankan workload. Jadi authorization antar node bisa saya ringkas dengan:

Manager Node:
    - control plane
    - workload
Worker Node:
    - workload

1 Cluster bisa terdiri dari:
    X Manager nodes >= 1 Manager Node
    X Worker nodes >= 0 Worker Node
Atau bisa dibilang, 1 cluster harus punya setidaknya 1 Manager Node, tetapi bisa terdiri dari banyak Manager dan Worker Nodes.

Workload vs Service vs Task
3 istilah ini terkadang membuat bingung satu sama lain.

Workload: adalah list pekerjaan yang harus dijalankan oleh Swarm Cluster dan diciptakan oleh Manager Node.
Service: kita sudah pernah memperlajari service di dalam Docker Compose, service adalah list requirement
    dalam bentuk blue print, atau keterangan detail dari apa yang workload ingin capai.
Task: adalah unit pekerjaan yang di jadwalkan untuk dikelola oleh para nodes sesuai dengan petunjuk pada
    service.

Perumpamaan: 
Workload: Saya ingin menjalankan usaha restoran sunda.
Service: Restoran ini harus memiliki 2 supervisor, 5 pelayan, luas dapur 2 x 5 meter, 
    dan setidaknya punya 2 cabang.
Task: Wujudkan cabang A di Jakarta dengan list karyawan yang sudah dibuat,
    Wujudkan cabang A di Bandung dengan list karyawan yang sudah dibuat.

Join Token: Sebuah token authentication yang digunakan sebagai password oleh Docker Engine lain
untuk bergabung ke dalam satu Swarm Cluster dan menjadi node bagi Swarm Cluster tersebut.
Token akan selalu diawali dengan SWMTKN yang merupakan singkatan dari SWarM ToKeN.
Contoh: SWMTKN-1-0kpmyi***

mutual TLS / mTLS : adalah singkatan dari mutual Transport Layer Security, adalah lapisan
enkapsulasi security dalam komunikasi antar node, dimana kedua belah pihak saling membuktikan
identitas dengan menggunakan special certificatenya. Itulah kenapa sebutannya mutual, karena bukan
satu node sebagai pembawa sertifikat dan satunya lagi sebagai pemeriksa, melainkan 2-2nya saling 
memberi sertifikat dan saling periksa.

Desired State: kondisi yang diinginkan (required condition) untuk terjadi yang tertera dengan jelas
    di dalam service dan oleh system akan dipertahankan agar tetap begitu. Atau dengan singkat
    bisa dibilang sebagai Kondisi Ideal.

Current State: adalah kondisi yang terjadi saat ini. Current State bisa sama dengan Desired State,
    tetapi bisa juga tidak sama. Current State yang tidak sama dengan Ideal State bisa dikatakan
    sebagai kondisi yang sedang tidak ideal. Kalau kondisi tidak ideal, maka cluster akan membawanya
    kondisi ideal, misalnya: kondisi ideal adalah backend memiliki 3 container replica, tapi saat ini
    cuma ada 2 container. Karena terjadi sesuatu 1 container down dan terhapus. Maka system akan
    menambahkan 1 lagi.

Dengan kemungkinan adanya multiple manager node dalam satu cluster dan kita juga mengenal konsep desired state, ini akan menjadi dilema. 
Bayangkan dalam satu team ada 2 atau lebih pemimpin yang masing-masing memiliki idealismenya sendiri-sendiri tentang bagaimana visi dan misi 
yang ideal dalam pekerjaan-pekerjaan yang dijalankan teamnya. Bagaimana antar manager bisa memiliki control yang selaras?
Atau bila seluruh visi-misi yang ideal semua di atur dan pegang oleh manager 1, apa yang terjadi bila manager 1 sedang down time? 
Apakah manager yang lain tau tentang desired state yang ideal seperti apa? (Single Point of Failure)
Hal ini diatas dengan adanya State Cluster dan algoritma Raft.

State Cluster / Distributed State Store: 
Seluruh instruksi, rancangan, desired state harus disimpan disuatu tempat. 
Tempat penyimpanan informasi tentang kondisi/keadaan cluster di simpan di dalam sebuah state yang
disebut juga State Cluster atau Distributed State Store. Mengapa disebut distributed? 
Sebab keberadaanya di-replika/di-duplikat dan dibagi ke beberapa manager node dan 
isinya harus konsisten walaupun berada di banyak Nodes.
(Kalau kita pikir-pikir mirip seperti Git Repository, Torrent file atau seperti Block-chain pada Bitcoin)

Raft: agar distributed information bersifat konsisten, pasti dibutuhkan semacam algoritma consensus.
Docker state cluster menggunakan Raft Consensus Algorithm untuk menjaga konsistensi ini.
Mirip seperti distributed repository seperti git, Raft juga menyimpan log perubahan yang terjadi pada state cluster.

State Cluster tidak hanya menyimpan desired state, tetapi juga menyimpan metadata yang dibutuhkan manager untuk mengelola cluster, seperti:
-) Node information: setiap informasi dan status dari node yang tergabung ke dalam clusternya.
-) Service information: segala informasi dari service yang dijalankan workload untuk cluster ini.
-) Task information: Informasi seluruh task yang dijalankan service.
-) Network Information: pada cluster tentunya lebih luas karena bisa sampai ke host lain.
-) Secret Information: informasi-informasi rahasia yang biasa disimpan docker secret seperti password (nanti akan dijelaskan).
-) Config Information: informasi-informasi konfigurasi yang biasa disimpan docker config (nanti akan dijelaskan).
dan lain sebagainya termasuk informasi yang menjadi data Raft Algorithm.

Stack: adalah sekumpulan Docker Service yang didefinisikan bersama dalam satu file Compose dan dideploy sebagai satu aplikasi ke Docker Swarm.
Kalau kita lihat seperti ini, sebuah stack sebenarnya seperti 1 buah docker compose project yang ditulis di dalam satu yaml file.
Di dalam docker swarm, stack juga ditulis di dalam yaml file dan bentuknya mirip sekali dengan docker compose project, tetapi sebenarnya dibalik
itu docker swarm menggunakan technology yang berbeda. Jadi apa yang dulu disebut 1 project sekarang menjadi 1 stack.


============= Manage Nodes =============

Pada praktek dasarnya untuk melakukan percobaan management node, kita memerlukan banyak host dengan 1 docker engine dan 1 node disetiap hostnya.
Tapi itu membutuhkan banyak pc. Bila tidak memakai banyak PC, kita bisa secara alternatif menggunakan Virtual Machine.
Tapi bahkan VM pun membutuhkan banyak resources performance dan memory.
Untuk contoh kali ini kita akan membuat Docker di dalam Container Docker, atau istilahnya Docker in Docker (Nested docker),
dimana setiap container akan kita jadikan satu host.

(Note: Menggunakan antara WSL dengan Docker Desktop langsung juga sedikit sulit, karena keberadaan linux di dalam WSL-nya tersembunyi)

Experiment itu bisa dicoba dengan menggunakan contoh di dalam Guides/Samurai

Untuk check node yand ada (harus dari manager node):
docker node ls

Untuk melihat existing join token dari manager node, dimana token tersebut digunakan untuk bergabung sebagai worker:
docker swarm join-token worker

Untuk melihat existing join token dari manager node, dimana to;ken tersebut digunakan untuk bergabung sebagai manager:
docker swarm join-token manager

Note, token yang dihasilkan akan berbeda antara join-token manager dan worker, contoh:
docker swarm join --token SWMTKN-1-0856h11hmx0u9ordbtv4lgqsybcduat0d7czh33yvm4jpngvxg-5rtlgosbrh3v27dvgretqzqf2 192.168.65.3:2377
docker swarm join --token SWMTKN-1-0856h11hmx0u9ordbtv4lgqsybcduat0d7czh33yvm4jpngvxg-26kd9yk20qb9lbd95jfcc3g65 192.168.65.3:2377

Dimana penjelasan feedback join token seperti dibawah ini:
docker swarm join --token SWMTKN-1-0kpmyi*** 192.168.65.3:2377
-) --token option memberi value token
-) SWMTKN (Swarm Token Prefix)
-) 192.168.65.3 --> Ip Address dari Manager Node
-) 2377 --> Port number dari control plane, yang digunakan untuk mengkomunikasikan management control antar node.

Untuk bisa menginvite node lain dengan meng-addvertise ip address manager pertama, kita bisa menggunakan
option --advertise-addr, dan ini jauh lebih best practice ketimbang langsung swarm init, jadi selalu biasakan advertise address:
docker swarm init --advertise-addr 192.168.1.10

Untuk tujuan security, kita juga mengenal option listener address.
Listener address cakupannya harus lebih luas atau sama dengan advertise address.
Dimana advertise address berguna untuk connection antar node, listener address adalah alamat yang
di dengar dari port manapun.

Kalau kita tidak membuat option listener address, maka secara default, node akan dengar dari semua source,
jadi seperti ini:
docker swarm init --listen-addr [address]:[swarm port]
docker swarm init --listen-addr 0.0.0.0:2377 

Kalau kita membuat command seperti ini:
docker swarm init --advertise-addr 192.168.1.10 --listen-addr 192.168.1.10:2377 
Itu artinya manager node tidak akan mendengar apapun selain 192.168.1.10:2377 untuk kebutuhan cluster, 
dari sisi security seluruh pintu swarm cluster tidak exist kecuali itu.

Mengapa advertise address lebih best practice? Karena ada kemungkinan manager node yang melakukan initiation
memiliki banyak virtual ethernet, misalnya 3, sehingga menghasilkan 3 ip address.
Kalau kita tidak advertise, algorithm docker swarm akan memilih kan kita 1 diantara 3 ip address itu secara otomatis.
Dan belum tentu pilihannya sesuai dengan pilihan kita.

Command untuk meninggalkan swarm cluster:
docker swarm leave

Jika Docker menolak leave karena node tersebut adalah Manager, Anda dapat menggunakan:
docker swarm leave --force

Untuk mempromosikan sebuah worker node menjadi manager node:
docker node promote [hostname]
contoh:
docker node promote masamune

Untuk membuat sebuah manager turun pangkat menjadi worker node:
docker node demote [hostname]
contoh:
docker node demote masamune

Untuk melihat detail informasi dan metadata sebuah node:
docker node inspect [hostname]
contoh:
docker node inspect tokugawa
untuk ke diri sendiri:
docker node inspect self

Untuk menghapus node (Pastikan node Status dalam keadaan down terlebih dahulu):
docker node rm [hostname]
docker node rm jinsuke

Bila kita memaksa menghapus sebuah node tanpa harus down terlebih dahulu, gunakan option force:
docker node rm [hostname] --force
docker node rm jinsuke --force

Di contoh ini total terdapat 9 nodes, diantaranya ada:

Semua bisa dicheck dari column MANAGER STATUS, yang kemungkinannya cuma berisi:
<blank> : artinya worker
Leader: jenis manager leader
Reachable: jenis manager biasa/non-leader
Unreachable: manager tidak bisa berkomunikasi dengan manager lain dengan Raft.

Di sini kita bisa melihat kalau bahkan manager node terdiri dari 2 macam, yaitu leader dan non-leader.
Manager leader di sini adalah nobunaga, yang menjadi swarm cluster initiator, lalu manager tokugawa dan hideyoshi yang
bergabung kemudian menjadi manager biasa.

Perbedaan manager leader dan non-leader adalah:
Leader adalah manager yang memiliki kemampuan untuk menerima perubahan cluster dan mengkoordinasikan Raft, dan jumlahnya pasti hanya 1.
Non-Leader adalah manager yang ikut membantu me-replica informasi State Cluster yang di share sesama manager.
    Manager yang non-leader juga bisa berpotensi untuk berubah menjadi leader kalau cluster kehilangan leadernya atau leadernya mati.
    Dan jumlah non-leader bisa banyak.

STATUS column sendiri bisa berisikan Ready atau Down, dimana sudah cukup jelas kalau Down artinya Node tidak bisa dihubungi sama sekali.

Kenapa saya membuat 3 managers di sini? Karena manager 3 adalah minimal gold standard dari jumlah manager di dalam sebuah cluster.
Bagaimana cara mengetahui jumlah manager yang baik dalam sebuah cluster? Sebelum tau cara mengetahui jumlah manager yang
bagus dalam satu cluster, kita harus paham dulu cara kerja consensus Raft antar managers.

Beberapa keputusan manager harus diproses secara demokrasi lewat vote antar manager. Bayangkan manager leader adalah seperti president dalam sebuah negara
atau CEO dalam sebuah perusahaan dan manager non-leader seperti wakil president dalam sebuah negara atau seperti board member di dalam sebuah
perusahaan. Tetapi di dalam docker, demokrasi hanya terjadi antar managers saja, workers sama sekali tidak ada suara dan pengaruh di sini.
Vote demokrasi ini adalah untuk 2 macam kategori kepentingan:
1. Leader Election: Pemilihan Leader yang baru jika leader yang lama mati.
2. Commiting Replication: Saat Leader mengambil keputusan untuk commit hasil rubah atau konfigurasi cluster, 
    setidaknya harus ada kata setuju dari para manager-manager lainnya.

Ketika kita membuat beberapa manager di beberapa host, tentu saja ada resiko dimana salah satu manager down, dan ini sangat beresiko.
Jadi untuk membuat rencana contingency salah satu manager down (terutama leadernya), kita membuat lebih dari satu manager.
Dan untuk kasus leader down, tentu saja harus ada Leader Election seperti yang sudah dijelaskan di atas.
Kurang lebih seperti seorang president yang memiliki wakil president, jika terjadi sesuatu dengan presidentnya, maka wakilnya akan
menggantikannya, karena bahaya sekali bila sebuah negara sama sekali tidak ada presidentnya. Tetapi bagaimana kalau wakilnya juga ikut down?
Lalu bagaimana kalau seorang president miliki 2 atau lebih wakil? Nanti wakil yang mana yang akan menggantikan presidentnya?

Untuk menyelesaikan masalah-masalah ini, docker swarm membuatkan sesuatu untuk kita. Docker swarm membuatkan kita jumlah Quorum.
    Quorum: adalah jumlah minimal para manager yang harus menyetujui sebuah keputusan yang dilandaskan sebuah vote.
        Note: jumlah quorum ditentukan oleh system dan tidak akan diupdate otomatis jika jumlah manager berkurang.
    Contingency: Dari jumlah quorum kita akan mendapatkan jumlah Contingency. Contingency adalah jumlah maximum TOLERANSI manager yang boleh down. 
        Jika manager yang down lebih daripada jumlah contingency akan mengakibatkan kekacauan.

Rumus menghitung Jumlah Quorum dan Contingency adalah:
-) Total = Jumlah total manager yang ada dalam swarm cluster
-) Quorum = ((Total / 2) floor) + 1
-) Contingency = Total - Quorum

Dari sini bisa saya buatkan hasil perhitungannya, jika:
Total: 1, Quorum: 1, Contingency 0
Total: 2, Quorum: 2, Contingency 0
Total: 3, Quorum: 2, Contingency 1
Total: 4, Quorum: 3, Contingency 1
Total: 5, Quorum: 3, Contingency 2
Total: 6, Quorum: 4, Contingency 2
Total: 7, Quorum: 4, Contingency 3
dan seterusnya...

Dari hasil perhitungan Quorum dan Contingency diatas, kurang lebih kesimpulannya seperti ini:
-) Jika manager hanya ada 1 orang, dia sudah pasti leader. Dan kalau dia down, contingencynya 0 dan swarm tidak ada manager sama sekali.
    Tamatlah sudah alkisah clusternya.
-) Jika manager ada 2 orang, setiap keputusan bisa dijalankan kalau yang vote setuju ada 2 manager minimal (quorum). Kalau leadernya down,
    maka sisa manager hanya 1 orang dan vote tidak bisa dilakukan sama sekali, karena vote valid kalau ada 2 manager yang jawab setuju.
    Tamatlah sudah alkisah clusternya.
-) Jika manager ada 3 orang, setiap keputusan bisa dijalankan kalau yang vote setuju ada 2 manager minimal. Kalau 1 manager down, masih
    akan ada 2 orang manager yang bisa melakukan pengambilan vote. Sekalipun yang down adalah leadernya, sisa 2 manager masih bisa
    melakukan pengambilan vote untuk siapa yang next jadi leadernya. Itu artinya kalau 1 manager down masih aman (contingency), kecuali kalau yang
    down ada lebih dari 1, maka bisa bahaya. Itulah kenapa 3 manager adalah minimum gold standard jumlah manager.
-) Jika manager ada 4 orang, jumlah pengambilan vote bisa di-sahkan kalau 3 manager bilang setuju. Itu artinya jumlah quorum meningkat, tapi
    jumlah contingencynya tidak bertambah kalau dibanding dengan total 3 manager. Dengan memiliki 4 manager, cluster masih takut kehilangan
    lebih dari 1 manager. Itu artinya kekuatan contingency dari 3 manager ke 4 manager tidak bertambah kuat.
-) Jika manager ada 5 orang, jumlah quorum vote tetap 3, tetapi kali ini cluster lebih kuat ban serepnya. Karena biarpun kehilangan 2 managers,
    cluster tetap akan baik-baik saja karena contingency bertambah kuat menjadi 2. Itu artinya 5 managers lebih toleran terhadap kegagalan daripada
    4 manager.

Kalau diperhatikan, selain total manager 1 atau 2, cluster akan berjalan dengan lebih aman bila ada manager down.
Tetapi kalau diperhatikan lebih lagi, peningkatan kekuatan contingency terjadi di setiap jumlah ganjil pada total managernya setelah
total 3 manager. Dimana ini menyimpulkan kalau peningkatan jumlah manager dalam angka genap itu sia-sia, 
karena yang ingin kita perkuat adalah contingencynya.

Oleh karena itu gold standard jumlah managers adalah: 3, 5, 7, 9, 11, 13, dan seterusnya.
Jadi selalu buat jumlah manager dari pilihan angka-angka itu.

Semakin tinggi angka contingencynya, semakin toleransi terhadap peristiwa yang membuat banyak node yang down,
maka dikatakan clusternya memiliki good or ideal HA (High Availability) configuration.

Bagaimana seorang manager tau kalau ada manager lain yang down atau kalau ada worker yang lain down?
Setiap manager mampu mengawasi workernya dengan monitoring lewat swarm node communication. Jadi manager terus menerus melakukan komunikasi
kepada workernya untuk memastikan worker masih baik-baik saja.
Tetapi sebuah manager bisa mengetahui keadaan lain managernya dengan mendengarkan Heartbeat (detak jantung) manager node lain.
Ya setiap manager node memiliki heartbeat yang secara terus menerus detaknya diperdengarkan di Raft consensus, sehingga sebuah manager
bisa mendeteksi kalau manager yang lain masih hidup atau mati.

Detak heartbeat sebuah manager node kurang lebih adalah setiap 1/10 detik, atau jantungnya berdetak 10 kali per setiap detiknya.
Ketika detak jantung sebuah leader berhenti, kurang lebih ada waktu 10 detik bagi manager non-leader lain untuk mengambil keputusan
kalau kita harus pilih ulang leader karena leader yang lama sudah mati. 10 detik itu disebut sebagai election timout. 

Voting ulang terjadi secara otomatis lewat perhitungan algoritma yang dilihat dari kecepatan waktu manager non-leader meresponse vote,
dan juga dari kelengkapan replica cluster state yang dia miliki. Sebagai pemakai docker kita tidak perlu terlalu memikirkan itu,
yang kita harus tau hanya kalau pemilihan vote next leadernya tidak terjadi secara random (walaupun terasa seperti random).

Dijelaskan diatas kalau angka quorum bersifat fixed dan tidak berubah secara otomatis ketika ada manager down dan jumlah total manager berkurang,
karena kalau jumlah quorum bisa secara otomatis ini bahaya sekali kalau misalnya terjadi kegagalan network partition misalnya, dimana
ada kendala sekelompok manager tidak bisa berkomunikasi dengan kelompok manager yang lain.
Misalnya seperti di perusahaan, ada 5 board member, diantaranya ada 1 CEO yang menghilang.
4 board member sisanya panik karena perusahaannya jalan tanpa CEO. Seharusnya CEO selanjutnya bisa disahkan kalau setidaknya
ada 3 diantar 4 orang itu setuju. Tapi sialnya terjadi partition, dimana board 1 dan 2 berada di indonesia dasn board ke 3 dan 4 berada di
Norwegia dan mereka tidak bisa bicara pisah negara. Board di indonesia akan dengan seenaknya merasa kita bisa memutuskan CEO berikutnya
hanya dengan 2 suara saja (si 1 dan 2 yang ada di Indonesia), tanpa memperdulikan eksistensi member ke 3 dan ke 4 di Norwegia.

(Note: kegagalan distributed information seperti ini pasti sering kalian alami dengan teman-teman. Kalian menyusun rencana jalan-jalan
bersama dimana semua orang boleh memberikan pendapatnya, tetapi ada teman kalian yang sakit pada saat meeting dan suaranya tidak diperdulikan.
Siapa suruh lu sakit waktu meeting! Jadi kita juga gak bisa dengar pendapat lu. Dan ini tidak baik.)

============= Update Nodes =============

Kita bisa mengupdate setiap node yang ada di dalam cluster dengan menggunakan manager node (Baik yang leader maupun yang non-leader).
Mengupdate sebuah node bisa menggunakan command:
docker node update [OPTIONS] [node hostname]

Kita akan melihat beberapa option yang mungkin sering digunakan.


1. Labeling

Seperti image atau container, kita juga bisa me-label sebuah node dengan tujuan penyisipan extra informasi atau metadata.
Untuk pemberian label kita bisa mengunakan command:

docker node update --label-add [key]=[value] [node]
docker node update --label-add storage="WD SSD blue edition 2 Tb" himura

Kalau mau pemberian lebih dari satu:
docker node update \
  --label-add type=database \
  --label-add storage="WD SSD blue edition 2 Tb" \
  --label-add "description=Primary Production Database Server" \
  tokugawa

(Note: Bisa di-check beragam syntax pemberian key-value pair pada label)

Kita bisa check hasil pemberian labelnya dengan:
docker node inspect [node]
docker node inspect tokugawa

Hasilnya bisa dilihat pada properties ini:
"Spec": {
    "Labels": {
        "description": "Primary Production Database Server",
        "storage": "WD SSD blue edition 2 Tb",
        "type": "database"
    },
    "Role": "manager",
    "Availability": "active"
}

Untuk menghapus label per-keynya, kita bisa menggunakan command:
docker node update --label-rm [key] [node]
docker node update --label-rm storage tokugawa

Untuk hapus lebih dari satu keys:
docker node update \
  --label-rm storage \
  --label-rm type \
  tokugawa


2. availability

Masih ingat ketika kita melihat list node dari cluster dengan menggunakan "docker node ls" command,
kita melihat ada column availability di resultnya.

ID                            HOSTNAME    STATUS    AVAILABILITY   MANAGER STATUS   ENGINE VERSION
4h7dn3zrxmr0tly8yr7nuh0ta     hideyoshi   Ready     Active         Reachable        29.7.2

Availability menentukan apakah node ini bisa digunakan untuk menempatkan atau memindahkan task/service.
Availability bukan berarti node tersebut hidup atau mati. Hidup atau mati di tentukan oleh column Status.

Ada 3 value availability, yaitu:
-) active: berarti node tersedia secara normal untuk menjalankan task.
-) pause: berarti node tidak menerima task baru, tetapi task yang sudah berjalan tetap berjalan.
-) drain: mengakibatkan 3 hal
    1) Mencegah task baru ditempatkan di node tersebut.
    2) Menghentikan task yang sedang berjalan di node tersebut.
    3) Scheduler kemudian akan mencoba menempatkan kembali task tersebut ke node lain yang tersedia.

Contoh commandnya seperti ini:
docker node update --availability [availability] [node]
docker node update --availability drain jinsuke


3. hostname

Kalau kita ada kebutuhan merubah hostname, kita bisa menggunakan docker node update
dengan option --hostname:
docker node update --hostname [newname] [oldname]
docker node update --hostname tokugawa-db tokugawa


4. role

Sebenarnya menggunakan option role fungsinya sama persis dengan docker node promote dan docker node demote.
Gunanya untuk merubah role node antara manager atau worker.

Kurang lebih commandnya seperti di bawah ini:
docker node update --role [role] [node]
docker node update --role manager jinsuke
docker node update --role worker tokugawa
